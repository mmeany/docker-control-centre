# Docker Control Centre: project guide

A Windows-first desktop app for managing a Docker engine, using the Windows
File Explorer model: tabs, a tree, an address bar you can type into, and
containers, projects, images, volumes and networks as folders. A second
layout, the dashboard (side nav, live overview, boards), can be chosen
instead. Built with
Tauri 2, React and Rust from the Tauri desktop template. Code is generated by
Claude to specs from the owner. `PLAN.md` holds the agreed decisions and
milestones.

## Architecture decisions (agreed; don't change without asking)

- **Shell:** Tauri 2. Uses the OS webview (WebView2 on Windows), so browser-engine
  security patches come from OS updates, not app rebuilds.
- **Frontend:** React + Vite + TypeScript. UI only: no secrets, no network calls,
  no file access. `src/api/` is the only place that calls Tauri, so the UI also
  runs in a plain browser (that's how `tools/ui-check` works).
- **Backend:** Rust does ALL file, network and OS work. Commands are thin;
  logic lives in modules with unit tests beside it.
- **Settings:** JSON at `<app config dir>/settings.json` (Windows:
  `%APPDATA%\com.mmeany.dockercontrolcentre\`). Non-secret only. Small
  per-section values go in `values` (keys prefixed with the section id); bigger
  data gets its own file. The bundle identifier names that folder, so don't
  change it after release.
- **Theme:** System / Light / Dark, saved in settings. System follows the OS
  live (dark if the OS can't say); the native title bar follows via `setTheme`
  (needs `core:window:allow-set-theme`). **All CSS colours are tokens** in
  `styles.css` with light AND dark values: never hard-code a colour in a rule.
- **Look and feel:** classic Explorer: tree on the LEFT, details list on the
  right, three toolbar rows (tabs + theme; command bar; back/forward/up +
  address bar + copy + refresh), status bar, Explorer keyboard shortcuts, 12px
  Segoe UI. The native title bar stays (no custom title bar).
- **Layouts:** Explorer (default) or dashboard, app-wide in settings values
  (`app.layout`, `shell/layout.ts`), switched live from Settings or a button in
  each layout. Both are views of one shell: `useAppShell` holds all state,
  runs every section hook and the keyboard; `ExplorerLayout` /
  `DashboardLayout` only place things. The dashboard drives the active tab
  (other tabs are kept), shows no tabs / address bar / view modes (their
  keys do nothing), and is roomier (13-14px). Sections may return a `board`
  for list levels, else their `content` shows. Pop-outs use the Explorer
  frame in both layouts. Nothing renders until settings load (no flash).
- **Places are addresses:** every view is a `Place`, copyable as
  `/<section>/<path>` and typeable in the address bar (`parseAddress`). Each
  tab has its own back / forward history (`state/tabs.ts`).
- **Engine:** one engine, via `bollard` over `DOCKER_HOST` (default
  `tcp://localhost:2375`, the WSL engine; `npipe://` and `unix://` also work;
  no TLS / SSH yet). Rust keeps one change feed (`watch_engine`, a Tauri
  `Channel`) that reports connected / disconnected and changes per resource;
  sections reload when `shell.engine.changes.<resource>` moves. No polling.
- **Compose:** `compose::Runner` is `Wsl { distro }` (`wsl.exe -d <distro>
  --cd <wsl path> -- docker compose ...`, the default on Windows: a WSL engine
  resolves bind mounts on the Linux side) or `Host`. Only allow-listed verbs
  run (`compose::verb_args`). Paths convert both ways (`E:\x` <-> `/mnt/e/x`,
  `\\wsl.localhost\<distro>\…`). wsl.exe's own messages are UTF-16LE
  (`decode_output`). Projects come from container labels plus pinned compose
  files (settings `compose.pinned`, named by `compose config`). Compose files
  are read in Rust (`compose_read_file`, 1 MB cap; WSL paths through
  `compose::readable_path`) and shown read-only; only .yml / .yaml files are
  handed to Explorer (`compose_show_file`). The resolved config
  (`config-yaml`) can hold .env secrets: fetched on request, never kept.
  Pins are `{ name, files }` (old `{ name, file }` still loads). Dropped
  files / folders are scanned in Rust (`compose_drop_candidates`: compose's
  default names, overrides, `compose-*` / `docker-compose-*` variants),
  confirmed with ticks in -f order, named by `compose_project_name` (only
  the name crosses to the UI), then pinned and brought up.

## Dependency policy

Minimise shipped dependencies; every addition needs a reason.
- Shipped JS: `react`, `react-dom`, `@tauri-apps/api`, `@xterm/xterm` +
  `@xterm/addon-fit` (the container terminal). No UI kit, no icon library, no
  state library, no chart library (stats draw SVG sparklines). Plain CSS.
- Rust: `tauri`, `tauri-plugin-dialog`, `serde`, `serde_json`
  (`preserve_order`), `tokio` (sync, fs, io-util, rt, time), `bollard`
  (features `http`, `pipe`: the Docker API), `futures-util` (streams), `bytes`
  (archive uploads; already in the tree through bollard). Tar is our own
  `tar.rs`, not a crate. Disable
  unneeded crate features. Run `cargo audit` before releases.
- Native dialogs are opened from Rust commands (`pick_folder`,
  `pick_open_file`, `pick_save_file`), so there is no JS dialog plugin and no
  dialog permissions in capabilities.
- Build tools (vite, typescript, tauri-cli, vitest) and Playwright (UI checks)
  aren't shipped.
- If the app needs TLS (HTTP clients, AWS SDK): rustls + ring, default features
  off, so Windows builds need only the MSVC Build Tools (no CMake/NASM, no
  OpenSSL).

### Shared components

- `FileList`: details (virtualised), list and tiles views (`view`, from
  `shell.view`; the shell keeps it per place). Sort, multi-select, keyboard,
  context menu, `dimmed` rows. Fixed ROW_H = 22px, must match `.fl-row` CSS.
- `Board`: the dashboard's list. Takes the same `columns` / `rows` as
  FileList and the section's selection and context menu; adds tick boxes,
  inline `actions(key)`, a More button (the context menu), a `bulk` bar for
  the selection, optional `childrenOf(key)` rows (a project's containers),
  and `layout="cards"`. Not virtualised (hundreds of rows, not thousands).
- Details pane: a section returns `details` (for the selection, else the open
  item); the shell shows it when the pane is on. `onDelete` handles Del.
- `TreeRow` / `TreeNote`: tree rows with twisty, selection, context menu.
- `CommandButton` / `CommandSeparator`: command-bar buttons.
- `FilterBox`: text filter with remembered history (`appApi.rememberFilter`),
  optional extra controls as children. `#filter-input` takes Ctrl+F if you wire it.
- `PageBar`: First / Previous / Next with a 100 / 500 / 1,000 page-size list.
- `ConfirmDialog` (`shell.ask`), `PromptDialog` (`shell.askName`, with
  validation), `TypedConfirmDialog` (`shell.confirmTyped`, for irreversible
  actions), `ContextMenu` (`shell.openMenu`).
- `ValueView` (text, or a DataTree for JSON), `ValueEditor` (JSON check,
  Format / Minify, optional masking), `DataTree` (expand all / to level, big
  arrays paged), `MaskedValue` (Reveal / Copy for secrets: plaintext only in
  component state), `DiffView` + `util/diff.ts`.
- `AboutDialog` (Help › About): name and version from `about_info`, the
  GitHub link (bugs and feature requests go there; `open_project_page`
  opens the fixed `PROJECT_URL` in Rust) and, last, the line "Lovingly
  created by Claude Code under the direction of Mark Meany." Keep both.
- `ErrorPanel` (in place of content, with Retry), `StatusBar`, `Toolbar`, `Icons`
  (inline SVG).
- CSS building blocks: `.section-pane`, `.filter-bar`, `.detail-view` +
  `.stat-tiles` + `.props-table` + `.props-section`, `.data-table`, `.kv-rows`,
  `.form-grid`, `.dialog` + `.dialog-wide` / `.preview-dialog`, `.segmented`,
  `.badge-info` / `.badge-warn`, `.warn-note` / `.ok-note`, `.progress`,
  `.live-dot`.

## Adding a section

1. `src/sections/<id>/use<Id>Section.tsx`: a hook taking `Shell`, returning
   `SectionUi`. Active when `shell.place.section === "<id>"`; `place.path` is
   whatever the section decides (folder, record id, "" for its root). For
   the dashboard, also return a `board` at list levels (a `Board` over the
   same rows) and, if other places should run its verbs, `act(key, verb)`
   going through the section's own confirmations.
2. Register it in `src/sections/index.ts` (name, description, icon, `root`,
   and `crumbs` / `parent` / `uri` if paths have levels).
3. Backend: `src-tauri/src/<id>.rs` (logic + tests) and
   `src-tauri/src/commands/<id>.rs` (thin commands), `pub mod <id>;` in
   `commands/mod.rs`, `mod <id>;` in `lib.rs`, commands in `generate_handler!`.
4. `src/api/<id>.ts` with typed wrappers.
5. Mock the new commands in `tools/ui-check/mock-ipc.js` and add a scenario.
6. Docs: README section list; this file.

`sections/containers` shows the patterns: a tree with expandable children, a
FileList per level, reloading on engine changes, a context menu with "Open in
new tab", and paths with their own parser (`isPath`).

## Rules

- Commands return `Result<T, AppError>`; the UI switches on `kind`
  (`notFound`, `accessDenied`, `invalid`, `other`). Add kinds in both
  `error.rs` and `api/core.ts`.
- Serde uses camelCase across the boundary. Tagged enums also need
  `rename_all_fields = "camelCase"`.
- State tied to a place (filters, page, search) is stored with the path it
  belongs to, so navigating can't apply it to another place for a render.
- Async effects guard against stale responses (`let stale = false` … cleanup).
- Destructive actions confirm; irreversible ones (deleting something that can't
  come back) use `shell.confirmTyped`.
- Secrets: never cached, logged or put in settings; reveal on demand only.
- Every user-facing string is plain English, sentence case; no exclamation marks.
- Explorer shortcuts: Enter open, Backspace / Alt+↑ up, Alt+← / Alt+→ back /
  forward, F5 refresh, Del delete, F2 rename, Ctrl+Shift+N new, Ctrl+E edit,
  Alt+Enter properties, Ctrl+T new tab, Ctrl+W close tab, Ctrl+Tab /
  Ctrl+Shift+Tab switch tab, Ctrl+L / Alt+D type an address, Ctrl+Shift+5 /
  6 / 7 list / details / tiles, Alt+Shift+P details pane.
- Engine lists reload from `shell.engine.changes`, never on a timer. The
  container list is shared as `shell.containers` (other sections show what
  uses what from it).
- Prune has no dry run in the engine: the preview is computed in
  `sections/rules.ts` and exactly those items are removed, one by one.
  Volumes are deleted with a typed confirmation; Docker's own networks
  (bridge, host, none) can't be deleted.
- Streams: start returns an id; stop it in the effect cleanup. The stats
  totals stream runs only while the dashboard overview is mounted; its 2 s
  tick paces messages to the UI and never polls the engine. Rust stops a
  window's streams, terminals and feed when it closes. A pop-out window
  (`?popout=<address>`) shows one place, has no `shell.popOut`, and never
  reads or writes the session.
- App shortcuts don't fire while focus is in a terminal (`.xterm`).
- Status colours come only from `src/status/status.ts` (tokens `--st-*` in
  styles.css, light and dark). Give tree rows and list rows a `status`; never
  colour by raw state. Prune candidates are built on the same model, so
  orange is exactly what "Orphaned only" removes.
- The tree (only) is filtered by `shell.treeLevel` with `partition()` from
  `status/filter.ts`: always keep the open item, end a branch with `TreeMore`
  ("+ n more") that reveals it until collapsed, reset reveals when the level
  changes. Badges count everything. Main lists are never filtered.
- Container files: folders are addresses (`…/web-1/files/etc/nginx`). Listing
  tries exec (a POSIX sh script with `stat`) and falls back to the archive API
  (stopped containers, no shell; capped at 64 MB read). Copy out saves a file
  as itself and a folder as .tar; copy in builds a tar in memory (512 MB cap).
  Drops from Explorer come through `shell.claimDrops`.
- File drops: the shell owns the window's one `onFileDrop` listener (never
  call it elsewhere). A mounted view that wants drops claims them
  (`shell.claimDrops`, latest wins, release in the effect cleanup);
  unclaimed drops go to a section's `fileDrop` (compose: confirm, pin, up).
  Drops while a dialog is open are ignored.

## Testing

- `cd src-tauri && cargo test`: unit tests (each module has its own).
- `cd src-tauri && cargo test --features integration`: against the real
  engine (DOCKER_HOST or tcp://localhost:2375).
- `npm test`: Vitest unit tests (paths, addresses, tabs).
- `npm run dev`, then open `http://localhost:1420/tools/ui-check/preview.html`:
  the UI in a browser with the IPC mocked (no Playwright needed). Drive the
  engine from the console with `window.__engine({...})`.
- `npm run build`: typecheck + frontend build.
- `npm run ui:check -- [scenario] [--light|--both]`: headless screenshots of the
  UI with the IPC mocked (`tools/ui-check/out/`). `UI_CHECK_PORT=1430` uses
  another port (another checkout's dev server may hold 1420, and an
  existing server on the port is reused). Needs Playwright once:
  `npm i -D playwright && npx playwright install chromium`. Look at the
  screenshots after UI changes, in both themes.

## Commands

- `npm install`: first time
- `npm run tauri dev`: run the app with hot reload
- `npm run tauri build`: release build + installers (`src-tauri/target/release/bundle/`)
- `npm run build`: typecheck + build frontend only
